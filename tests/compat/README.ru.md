# Матрицы совместимости с Linux

Набор проверок разделяет четыре вида свидетельств. Успех на одном уровне
нельзя считать успехом на другом.

| Уровень | Что он подтверждает | Что он не подтверждает |
| --- | --- | --- |
| манифест образа | именованный контейнерный образ был доступен в реестре в момент проверки | двоичную совместимость или поддержку во время работы |
| smoke-тест статической сборки с musl | оба файла могут запуститься и вывести `--version` в пользовательской среде образа | загрузку init, интеграцию с libc, инструменты фаервола, функции ядра, NFQUEUE или корректность политики |
| перекрёстный `cargo check` | рабочее пространство проходит проверку типов для установленной стандартной библиотеки Rust-цели | компоновку, запуск, поведение оборудования, ABI ядра или упаковку |
| стенд парсеров и супервизоров init | дерево установки, выбранные парсеры, сценарии жизненного цикла и помощник группы в изолированном стенде | реальную загрузку или реальную политику фаервола |

Реальный сценарий перехода из Learning в Enforcing — отдельный сквозной тест.

## Релизная проверка и исследование совместимости

У релизного процесса есть отдельная авторитетная матрица:
[`packaging/ci/release-matrix.json`](../../packaging/ci/release-matrix.json).
Она задаёт 43 строки двоичных файлов, 43 соответствующие строки
пакетов и ровно 86 пар пользовательской среды дистрибутива и
OCI-платформы. В каждой из них требуется установить релизный пакет и
успешно выполнить назначенные контейнерные тесты. Каждая строка
платформы разворачивается в оба бэкенда фаервола, что даёт 172 задания
firewall E2E. Граф зависимостей релиза:

```text
Validation
    -> Quality Gate
    -> Binaries
    -> Packages
    -> Install Matrix
    -> Container Tests
    -> Firewall E2E
    -> Release Evidence
    -> Publish
```

Полная политика, уровни архитектурных свидетельств и граница публикации описаны
в [руководстве по релизному CI](../../.github/README-CI.ru.md). Компиляция
разрешается только после Validation и Quality Gate. Публикация разрешается
только после того, как этап evidence сверит каждую обязательную строку матрицы
и каждый релизный файл.

86 релизных строк охватывают Debian 12/13, Ubuntu 22.04/24.04/26.04,
Fedora 43/44, Rocky Linux 9/10, AlmaLinux 9/10, openSUSE Leap 16.0,
Tumbleweed, Alpine 3.23/3.24 и Arch Linux. В них включены все выбранные
платформы соответствующих официальных образов: `amd64`, `386`, ARMv5,
ARMv6, ARMv7, `arm64`, `ppc64le`, `riscv64` и `s390x`, где они доступны.
Двоичный файл и пакет для семейства/архитектуры можно собрать один
раз, но установка, контейнерные тесты и результаты обоих бэкендов
остаются отдельными для каждой пары дистрибутива и платформы.

Эта релизная матрица и описанная ниже исследовательская матрица из 60 строк
решают разные задачи. Успех широкого smoke-теста совместимости не добавляет
релизную строку, а удаление архивного исследовательского образа не меняет
контракт поддержки пакетов. Нельзя выводить релизные гарантии из
`distros.tsv`.

## Матрица образов дистрибутивов

`distros.tsv` содержит ровно 60 строк для Debian/Ubuntu, Alpine, Fedora,
Rocky, AlmaLinux, CentOS Stream, Oracle Linux, openSUSE, Amazon Linux, Arch,
Gentoo, Void, Devuan и Artix. В ней намеренно есть поддерживаемые,
непрерывно обновляемые, устаревшие и архивные выпуски примерно за предыдущие десять лет. Столбец
жизненного цикла описывает строку образа, а не обязательство проекта по поддержке.

Проверка синтаксиса матрицы и числа строк без Docker:

```console
scripts/test-distro-matrix.sh validate
```

Проверка манифестов в реестрах:

```console
scripts/test-distro-matrix.sh manifests
```

Запуск матрицы с каталогом, который содержит статически скомпонованные с musl
`openshield-daemon` и `openshield-tui`:

```console
scripts/test-distro-matrix.sh smoke /absolute/musl/release-directory
```

`smoke` требует локальную Unix-сокетную конечную точку Docker и отключает сеть
каждого тестового контейнера, монтирует двоичные файлы и корневую файловую
систему только для чтения, сбрасывает все полномочия и включает
`no-new-privileges`. Он не удаляет образы, чтобы не конфликтовать с другими
локальными пользователями Docker. `smoke-clean` сохранён как устаревший
недеструктивный псевдоним для `smoke`. Завершённый прогон на итоговых статических PIE-артефактах
вывел `matrix rows: 60; failures: 0`; оба двоичных файла выполнили `--version` в каждой строке.

Этот результат прежде всего подтверждает переносимость выбранных статических musl-артефактов
между этими пользовательскими средами. Контейнеры совместно используют ядро хоста, а
`--version` намеренно не инициализирует атрибуцию procfs или бэкенды фаервола. Это не
сертификация 60 полных дистрибутивов.

## Матрица целей Rust

`targets.tsv` содержит 25 встроенных имен Linux-целей. Проверка файла:

```console
scripts/check-target-matrix.sh validate
```

В среде Rust 1.98.0 с rustup установите отсутствующие стабильные цели и проверьте типы:

```console
scripts/check-target-matrix.sh check --install
```

Стенд выполняет проверки целей с одним заданием Cargo, чтобы ограничить пиковое потребление
памяти и обеспечить детерминированную работу на узлах с ограниченными ресурсами.

Завершённый стабильный прогон проверил 23/23 доступных стабильных целей без ошибок:

| Семейство архитектур | Охваченные варианты |
| --- | --- |
| x86 | i586 и i686; GNU и musl, где указано |
| x86_64 / amd64 | GNU и musl |
| ARM | ARMv5, ARMv6 и ARMv7; программная и аппаратная плавающая точка, где её предоставляет Rust-цель; GNU и musl по списку |
| arm64 / aarch64 | GNU и musl |
| PowerPC 64 LE | `powerpc64le` GNU |
| IBM Z | `s390x` GNU |
| RISC-V 64 | `riscv64gc` GNU/musl и `riscv64a23` GNU |

`riscv32gc-unknown-linux-gnu` и
`riscv32gc-unknown-linux-musl` записаны как Tier 3 Rust. Стабильный rustup не
предоставляет для них стандартную библиотеку, поэтому стабильная матрица их пропускает.
Для сборки нужен отдельно проверенный процесс на nightly с `build-std`; они не заявлены как
стабильные релизные цели.

В workflow заданы 43 строки релизных двоичных артефактов; каждый из них должен быть
скомпонован, проверен на ожидаемую ELF-идентичность и статическую границу среды
выполнения, а затем пройти smoke-запуск в закреплённом образе целевого семейства и
архитектуры. Задания `amd64` и `arm64` используют нативные исполнители x86-64 и AArch64. Для `386`
используется режим совместимости x86. ARMv5, ARMv6, ARMv7, `ppc64le`,
`riscv64` и `s390x` используют закреплённые по digest сборочные образы Cross и
выбранный обработчик QEMU user mode на одноразовых исполнителях GitHub.
Привилегированная регистрация обработчика запрещена на self-hosted исполнителях.

Для публикуемого релиза все 86 строк с установленными пакетами должны пройти
полные сценарии обоих бэкендов, включая эмулируемые строки. Для строк QEMU небольшой отдельно
собранный статический TCP/UDP-клиент нативной архитектуры хоста обеспечивает
стабильную идентичность исполняемого файла для проверок правил приложения;
демон, пакет, команды фаервола и целевая пользовательская среда остаются
выбранной иностранной архитектуры. Это корректное свидетельство работы в эмуляции,
но не нативное выполнение, не проверка ядра дистрибутива и не сертификация
физического оборудования. Общая гарантия работы на оборудовании x86, ARM,
arm64, PowerPC, IBM Z и RISC-V не даётся. Псевдонимы
архитектур не создают новых целей:
AMD64 — это x86_64, ARM64 — AArch64, а отдельного имени Rust-цели `aarch` нет.

## Матрица систем инициализации

Проверка исходных файлов и дерева без Docker:

```console
scripts/test-init-matrix.sh validate
```

Изолированные стенды парсеров и супервизоров:

```console
scripts/test-init-matrix.sh manifests
scripts/test-init-matrix.sh containers-clean
```

Завершённые проверки охватили деревья установки для всех шести систем, разбор
OpenRC, семантику PID/исполняемого файла SysVinit, сценарии старта/завершения и карантина
runit и s6, компиляцию зависимостей s6, разбор dinit, а также создание группы через
BusyBox `addgroup` и shadow `groupadd`. systemd подготавливается статически и
проверяется отдельно: unit-файл с заглушками целей прошёл `systemd-analyze verify`,
а автономная команда `systemd-analyze security --offline=yes --threshold=100`
прошла с оценкой поверхности 2,7 (`OK`). Проверка и та же оценка 2,7 были
повторены с systemd, установленным внутри закреплённого контейнера Tumbleweed.
Матрица не загружает systemd в контейнере и не запускает его как PID 1.
Полная декларация создания и перемаркировки tmpfiles для runtime-каталога, каталога состояния и общей
блокировки xtables также прошла повторное применение и проверку точных метаданных.

В стендах жизненного цикла демон заменён заглушкой. Их успех не означает, что был
выбран бэкенд или фильтровались реальные пакеты.

## Реальный сквозной сценарий фаервола

В workflow каждая из 86 строк релизных платформ разворачивается в два полных сценария
Learning-to-Enforcing: с приоритетом nftables при наличии обоих интерфейсов и без
команды `nft`, когда должен быть выбран полный резервный набор iptables/ip6tables.
Публикуемый релиз должен пройти 86 заданий nftables и 86 заданий iptables, включая DEB, RPM,
APK, Arch, нативные строки, режим совместимости x86 и QEMU user mode.
Стенд явно устанавливает запрошенный бэкенд до установки релизного пакета;
эта настройка теста сама по себе не меняет и не расширяет метаданные зависимостей
формата пакета.

Каждый релизный образ закреплён SHA-256 digest и связан с явной OCI-платформой.
Этап evidence записывает идентичность образа и платформы, хеши пакета и
двоичных файлов, результат установки, назначенные результаты бэкендов и
ожидаемый список релизных файлов. Docker всё равно использует ядро исполнителя,
поэтому результаты проверяют пользовательскую среду контейнера и поведение в
изолированном сетевом пространстве имён, а не собственное ядро дистрибутива или
полный процесс загрузки init.

`../e2e/server-learning-enforcing.sh` создаёт одноразовую сеть Docker с клиентом и HTTP-сервером.
Он предназначен для раздельной проверки каждого бэкенда:

- выбора запрошенного бэкенда nftables или iptables;
- исходного сохраняемого режима `Learning` после стартового карантина;
- доступа к наблюдению для `openshield` и отказа постороннему пользователю;
- отказа в управлении не-root члену группы;
- изучения привязанных к приложению правил TCP и UDP;
- продолжения доступа для изученного исполняемого файла и отказа другому в
  `Enforcing`;
- совместной работы с последующим запретом другого фаервола;
- отказа входящему трафику с последующим явным разрешением;
- карантина `BlockAll` в ядре при штатной остановке без замены сохранённого `Enforcing`;
- перезапуска в сохранённый режим.

Соберите демон, совместимый с выбранной пользовательской средой клиента, затем
явно запустите каждый бэкенд. По умолчанию используется Debian Bookworm:

```console
tests/e2e/server-learning-enforcing.sh nftables /absolute/bookworm/release-directory
tests/e2e/server-learning-enforcing.sh iptables /absolute/bookworm/release-directory
```

Закреплённый снимок Tumbleweed выбирается без изменения сценария:

```console
CLIENT_FAMILY=tumbleweed CLIENT_IMAGE='opensuse/tumbleweed@sha256:8f6397b7b7ebc78e111d9a13fb2b157664ad5524e1f3b908deb45938b3095045' \
  tests/e2e/server-learning-enforcing.sh nftables /absolute/tumbleweed/release-directory
CLIENT_FAMILY=tumbleweed CLIENT_IMAGE='opensuse/tumbleweed@sha256:8f6397b7b7ebc78e111d9a13fb2b157664ad5524e1f3b908deb45938b3095045' \
  tests/e2e/server-learning-enforcing.sh iptables /absolute/tumbleweed/release-directory
```

Сценарий устанавливает пакеты в одноразовом клиентском контейнере, поэтому ему нужен доступ
к реестру и сети пакетов. Полномочия фаервола даются только этому контейнеру;
сценарий не применяет правила к хосту. До создания ресурсов он читает активную точку подключения
через `docker context inspect` и отказывается работать с любым URI, не соответствующим `unix:///*`.

Каждая успешная релизная строка отчитывается о двух прогонах бэкендов в
выбранной пользовательской среде:

```text
PASS server Learning -> UDP/TCP Enforcing -> inbound allow -> restart (nftables)
PASS server Learning -> UDP/TCP Enforcing -> inbound allow -> restart (iptables)
```

В прогоне nftables установлены оба интерфейса, и должен быть выбран nftables. В
прогоне iptables команда `nft` отсутствует, и должен быть выбран бэкенд совместимости.
Такая пара проверяет именно приоритет и резервный выбор, а не только принудительно заданное имя.

Успешная пара прогонов охватывает работу сценария внутри одноразовых сетевых и
контейнерных пространств имён локального Docker Engine через Unix-сокет. Она не проверяет и не
изменяет фаервол хоста и не сертифицирует ядра, развёртывания, обновления или совместную работу с
конкурирующими конфигурациями фаервола.
